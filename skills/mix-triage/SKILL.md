# Triage

Move issues on the project's tracker through a small state machine. Triage is for work that
**arrives raw** (bug reports, feature requests, external PRs). Stories created by `/mix-tasks`
are already specified; they skip triage.

**Context**: call the Skill tool with `mix-scope` for the project: its repos, glossary, ADRs, and
the `tracker` block of its `mix.yml` (`type`, `labels`, `access`, `triage_prs`, `notes`), plus
`mix-dev-skills/out-of-scope/` for rejected requests. No tracker configured →
ask how issues are reached (MCP server, `gh`, `glab`, a CLI, or pasted text) and suggest
`/mix-setup` once.

## Writes need a yes

Every change on the tracker (label, comment, close, new issue) is visible to others. Show the
exact change first and apply it only after the user confirms. With `tracker.access: read-only`,
nothing is written: briefs and notes are saved locally under `mix-dev-skills/triage/<issue-id>.md` and
shown to the user to post where they choose.

Every comment posted on the tracker starts with:

```
> *This was generated by AI during triage.*
```

## Roles

Two **category** roles: `bug` (something is broken), `enhancement` (new feature or improvement).

Five **state** roles:

- `needs-triage`: the maintainer needs to evaluate it.
- `needs-info`: waiting on the reporter.
- `ready-for-agent`: fully specified, an agent can take it without a human.
- `ready-for-human`: needs a human (judgement calls, external access, design, manual testing).
- `wontfix`: will not be actioned.

Each triaged item carries one category and one state. Label strings come from `tracker.labels`
(defaults: the role names). Conflicting states → flag it and ask before anything else.

Transitions: unlabeled → `needs-triage` → `needs-info` / `ready-for-agent` / `ready-for-human` /
`wontfix`. `needs-info` returns to `needs-triage` when the reporter answers. The maintainer can
override anytime; flag transitions that look unusual.

**External PRs** (when `tracker.triage_prs: true`): a PR is an issue with attached code, same
roles and states. `ready-for-agent` means a brief is attached for an agent to finish the diff;
`ready-for-human` means ready for a human to merge. Discovery lists only PRs from outside the
team; a PR the user names is always triaged.

## What needs attention

Query the tracker and show three buckets, oldest first: **unlabeled**; **`needs-triage`**;
**`needs-info` with reporter activity since the last triage notes**. Tag each line `[issue]` or
`[PR]`, with a one-line summary and counts. Let the user pick.

## Triage one item

1. **Gather.** Read the full item (body, comments, labels, author, dates; the diff for a PR).
   Parse prior triage notes so resolved questions aren't re-asked. Explore the code in glossary
   terms; in multi-repo projects, find which repo(s) the item belongs to from their roles. Then:
   - **Redundancy**: search for an existing implementation of the requested behaviour by domain
     concept, not just the request's words; report where you looked.
   - **Prior rejection**: read the out-of-scope folder and surface any match
     ([OUT-OF-SCOPE.md](OUT-OF-SCOPE.md)).
2. **Recommend** a category and state with reasoning, plus a short summary of the relevant code
   (including whether it already exists). Wait for direction.
3. **Verify the claim** before grilling. A bug: reproduce it from the reporter's steps (call the
   Skill tool with `mix-diagnose` when it resists a first attempt). A PR: confirm the diff does
   what it claims, in a separate worktree so the user's working copy is untouched, running the
   relevant tests. Report: confirmed (with the code path), failed, or not enough detail (a strong
   `needs-info` signal).
4. **Grill** when the request needs shaping: call the Skill tool with `mix-grill`, which also
   keeps the glossary and ADRs current.
5. **Apply the outcome** (after the user confirms the exact change):
   - `ready-for-agent`: post an agent brief ([AGENT-BRIEF.md](AGENT-BRIEF.md)). Large
     enhancements → suggest `/mix-specify --quick` from the brief instead of a single ticket.
   - `ready-for-human`: the same brief, plus why it can't be delegated.
   - `needs-info`: post triage notes (template below).
   - `wontfix`, by reason: **already implemented** → point to where it lives, no out-of-scope
     entry; **rejected bug** → polite explanation, close; **rejected enhancement** → write the
     out-of-scope entry, link it in the comment, close.
   - `needs-triage`: apply the role; comment only if there is partial progress.

## Quick state override

"Move #42 to ready-for-agent" → trust the maintainer: confirm the exact change (labels, comment,
close), then act, skipping the grilling. Moving to `ready-for-agent` without a grilling session →
ask whether they want an agent brief written.

## Needs-info template

```markdown
## Triage Notes

**What we've established so far:**

- point 1

**What we still need from you (@reporter):**

- question 1
```

Everything resolved during grilling goes under "established". Questions are specific and
actionable, never "please provide more info".

## Resuming

Prior triage notes exist → read them, check whether the reporter answered, and present the
updated picture before continuing.
